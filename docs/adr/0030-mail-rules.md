# 规则：收到邮件时按条件自动执行的一串动作

**规则**是用户建的「当 … 如果 … 就 …」：一个触发、一组条件（全部满足或任一满足）、一串按顺序执行的动作。它在拥有者里、本机执行，不下发到服务器。Godwit 不自动创建任何规则；「可疑邮件移到垃圾邮件」这类常用组合只作为新建时可选的模板。定期清空废纸篓和垃圾邮件要彻底删除，规则做不到，所以它照旧是账户设置里的自动清除（`Purges`），规则页只放一个指过去的链接。

触发有四种：收到新邮件、被打上某个标签、安全判定为某一级、每天第一次同步。触发可以限定在某一个账户的邮件上，规则里存账户的 id，不存显示名；不限定就是所有账户。应用退出期间到的邮件在下次同步时补跑。运行方式按规则设置，分「仅在窗口打开时」（默认）和「后台运行」：任一启用的规则选择后台运行时，窗口关闭后 Godwit 保留在菜单栏继续同步，和全局的「后台常驻」（`KeepInBackground`）是或的关系；这样不必为一两条规则让整个应用常驻。新建或修改规则时，用户可以选择对现有符合条件的邮件执行一次，外发和 AI 动作除外；「每天第一次同步」触发的规则同样跳过这两类动作，它们只处理新到的、刚被打上标签或刚有安全判定的邮件，不会把旧邮件发出去。

动作分四类，按会发生什么决定保存时要什么：

- **本地**：打/去标签、已读、星标、归档、移到垃圾邮件或废纸篓、不再执行后续规则。可以撤销，保存不需要额外确认。规则不能删除或彻底清除邮件。
- **转发**：规则里的收件人是 [0003](0003-no-extension-can-send.md) 说的「会在之后自动外发的持久状态」。保存含转发的规则、改动收件人，都要一张写明收件人的确认卡片，用户在 Godwit 里点确认才生效；Wit 只能提议规则：在对话里给出预览卡片，列出触发、条件、动作和转发收件人，用户确认收件人后自己点保存，或带着它进编辑器修改；Wit 不能替用户确认或保存。转发照常进发件箱，走 [0006](0006-send-at-most-once.md) 的至多一次，审计记为规则发送。
- **写文件**：导出 PDF / EML、保存附件，写到用户选的本机文件夹。默认每封邮件一个子文件夹，名字是「收信日期 主题」（如 `2026-11-03 Invoice #1234`），也可以选「发件人 / 日期 主题」「年 / 月 / 日期 主题」，或用变量块自定义；模板存成 `{date} {subject}` 这类稳定的 id，界面按语言显示。变量的值来自邮件，填进去前去掉路径分隔和控制字符，所以目录层级只能来自模板里的 `/`，路径也出不了目标文件夹。同一条规则写到同一个目标的文件都放进这个子文件夹；PDF 和 EML 与子文件夹同名，附件保留原名，正文里的内嵌图片不保存。从不覆盖或删除已有文件，重名加编号；实际写出的路径记在动作结果里，重试时沿用。目标文件夹不存在时动作失败，不自动创建。
- **AI**：起草回复草稿、提取要点。会自动把邮件发给模型，按 [0010](0010-ai-off-by-default.md) 默认关闭，用户在「智能」里单独打开后才能选；发出前照常脱敏（[0025](0025-mask-at-cloud-egress.md)），起草的结果只是草稿。

规则打的标签记为一种单独的来源，手动操作仍然优先（修订 [0014](0014-labels-local-manual-wins.md)）：用户手动去掉的标签，规则不会再加回来。

每条规则保留最近命中的邮件和每个动作的结果。本地动作可以从这里撤销；转发、导出已经发生，只能查看。

屏蔽发件人也是本地动作，可以对现有邮件运行。屏蔽名单和动作的原状态、结果在同一事务里提交；地址无效或名单已满时只记该动作失败，不阻塞后续规则事件。撤销用记录里的地址，不依赖原邮件仍然存在；已有的屏蔽以及用户后来解除后重新设置的屏蔽不会被撤销。会话列表的屏蔽入口取最新一封非本人、非已发送或草稿邮件的发件人，避免把自己的回复作为屏蔽目标。

规则存成带版本号的 JSON：触发、全部或任一条件、有序动作，和编辑器的状态一一对应，保存时按动作白名单校验。JSON 里的固定常量都是稳定的英文 id，界面按语言显示：触发、字段、比较、动作是 `receive`、`subject`、`contains`、`archive` 这类；有无附件是 `yes`/`no`，安全判定是 `suspicious`/`dangerous`；标签存 slug（[0014](0014-labels-local-manual-wins.md)，预置的如 `otp`，用户建的是 `u` 加 id），文件夹存角色或文件夹 id，不存显示名。只有规则名、条件里用户输入的文字、收件人和本机路径是用户自己的数据，原样保存。条件用 Go 的 switch 求值，不引入表达式引擎。编辑器预览把条件编译成 SQLite 查询，主题、发件人、正文走已有的 `messages_fts`。

执行接在 `events_log` 上：规则引擎和插件 Hook 一样是一个游标消费者，在拥有者的后台 goroutine 里读日志，不阻塞同步和界面。应用退出期间到的邮件，下次同步写进日志后自然补上；「后台运行」只决定关窗后这个消费者是否继续。一封邮件对一条规则只处理一次：先按 (规则, 邮件) 唯一键写下运行记录，再逐个执行动作，每个动作单独记结果和撤销所需的原状态；崩溃重启后只接着做没完成的动作。对现有邮件执行一次是同一套流程，换一个触发值。

## Considered Options

- **通用工作流引擎**（PR #434）：五个阶段、十八种动作、自动创建默认开启的预设、免审批的转发。能力最全，但概念太多，转发和 Wit 建规则都绕过了 [0003](0003-no-extension-can-send.md) 和 [0004](0004-permission-gateway-taint.md)。
- **自由画布编辑器**：能画分支，但邮件规则几乎都是一条直线，画布要新写组件，窄窗口也放不下。选了竖排的节点卡片：触发、条件、动作各一张，箭头相连，可以增删和排序。
- **下发成服务器过滤器**（Sieve、Gmail filter）：应用不开也生效，但各服务商能力不同，标签只存本地也下发不了；以后可以把纯移动类的规则单独下发。
- **规则只对之后的邮件生效**：最简单，但用户建规则多半就是为了收拾现有的邮件。
- **用 cel-go 或 expr 表示条件**：两者都能保证求值会结束，CEL 还能估算和限制开销。但用户是点选条件，不写表达式；预览的瓶颈在读邮件，不在求值；表达式文本也难以还原回编辑器、翻译成 Sieve。cel-go 还会带进 protobuf 和 ANTLR。以后开放手写的「高级条件」时，再作为一种条件叶子加进来，届时优先 CEL。
- **规则引擎（grule 等）**：靠反复触发直到事实不再变化来推导，和「每封邮件只处理一次」相反。
- **Sieve 作为本地格式**：没有本地标签、导出、AI、撤销，也没有触发的概念；Go 实现还不成熟。只把能表达的子集作为以后的导出格式。
- **SQLite 任务队列库**（goqite、backlite、River 的 SQLite 驱动）：只给「至少一次」，幂等、命中记录和撤销还是要自己写，不如直接用运行记录表。
- **沿用 PR #434 的执行方式**：在同步、打标签和安全扫描的路径里同步执行，动作全做完才写运行记录，崩溃后会重复转发；「收到新邮件」也没有接上。条件匹配、动作排序和互斥校验可以复用。

## Consequences

- 规则执行是一种新的外发来源：审计要能区分「用户发送」「MCP 发送」和「规则转发」，并指回是哪条规则。
- Wit 建规则的工具只能产生一份待用户确认的规则，名字和描述要说清楚这一点（AGENTS.md「名字就是承诺」）。
- 规则执行要防循环：规则转发出去的邮件带标记；带标记的邮件只跳过转发，它的本地动作照常执行；规则打标签引起的「被打上标签」只传一层。
- 转发走撰写的正常入队路径，带上原邮件附件和审计来源，不直接写发件箱表。
- 条件的种类要守住白名单，并限制条件数和输入大小，别让 JSON 结构慢慢长成一门语言。
- `events_log` 的清理只删所有游标都已越过的事件，所以规则的游标要登记在清理会看的地方（`plugin_cursors` 或同等的表），否则关机超过 7 天的邮件会被清掉而漏跑。
