# 原生插件是可信代码，跑在子进程里

原生插件 = `plugin.json` + 一个平台专用动态库，通过稳定的 C ABI（`godwit_plugin_init` + 函数表，JSON 负载）调用。这是**可信代码执行机制，不是沙箱**：原生代码以 Godwit 的全部权限运行，文档和界面都不能暗示有任何约束；脚本插件的 `mail` / `net` 权限卡片不套用到原生插件上。

每个启用的原生插件由一个子进程 `godwit plugin-host` 加载，核心和子进程之间走 stdio 上的 JSON 行协议。所有校验和授权都在**加载之前**完成：子进程先算库文件的 sha256，和授权的哈希不一致就退出、不 dlopen。授权绑定具体文件（`permission_hash` 就是安装快照的 `source_hash`），文件变一个字节就要重新授权。

## Considered Options

- **在主进程里 dlopen**（原型的做法）：插件崩溃会带崩邮件客户端；Go c-shared 库不能安全 dlclose，停用、升级都要重启应用；Windows 上加载中的 DLL 删不掉；ABI 没有取消，超时只能干等。子进程方案里这些都变成 kill 进程。
- **插件直接是一个可执行文件**（像 MCP 一样走 stdio）：代码更少，但用户定了动态库方向，而且动态库让宿主控制进程本身。

## Consequences

- 插件返回的 `ok: false` 信封（限流、上游错误）是正常业务结果，不计失败；只有 ABI 错误、超时、子进程退出才计一次，连续三次停用。
- 子进程退出后不立即重启，下次调用时懒启动；每个新进程都先核对 `describe`、再下发当前配置。
