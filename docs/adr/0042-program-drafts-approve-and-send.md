# 程序写的草稿打本地标记，「批准并发送」绑定用户看到的那一版

用户已经在用脚本和 AI 工具整理邮件、写草稿，安全的分工是「程序起草、用户发送」（[0003](0003-no-extension-can-send.md)）。但程序写的草稿和用户自己的看起来一样，用户分不出哪封要仔细读，也只能打开撰写窗口再发。所以 Godwit 给程序写的草稿打上标记：会话里在往来邮件下面列出程序写给这个会话的回复和转发草稿，草稿文件夹里也显示「来自程序的草稿」，并给出一个「批准并发送」按钮（#671）。

**谁算程序。** 下列途径创建或修改草稿时写入标记：本机 API 的 `full` 和 `mcp` 角色（[0002](0002-single-owner-local-api.md)，即用户的程序和 `godwit mcp`），插件的 `mail:write`（`createDraft`、`updateDraft`），以及 Wit（`create_draft`、回复和转发草稿、撰写窗口里的修改，规则的「起草回复」）。程序给已有草稿加删附件、换发件账户也算修改。用户在 Godwit 界面里的操作不算：撰写窗口、快速回复、mailto 退订生成的草稿都不打标记。

**标记只存在本地。** 它是 `drafts.from_program` 一列，不是 IMAP keyword：任何 IMAP 客户端都能给邮件加 keyword，用它当标记就能被伪造，也能被别的客户端去掉；Godwit 的草稿本来也只存在本地。

**用户自己改过也不去掉标记。** 标记的意思是「这封草稿里有程序写的内容」，不是「用户还没看过」。用户改一个字不代表读过了其余部分，去掉标记反而会让程序的文字失去提醒；而且撰写窗口会自动保存，很难区分「用户改过」和「用户打开过」。标记在草稿发出或删除时随草稿一起消失。

**批准绑定版本。** 界面调用 `ApproveDraft(draftID, revision)`，`revision` 是界面上显示的那一版。存储的 revision 不同（程序在用户看过之后又改了），就返回 `ErrStaleDraft`，什么也不发，界面重新读取后用户要再批准一次。没有标记的草稿返回 `ErrNotProgramDraft`。

**发送路径和撰写窗口相同。** `ApproveDraft` 内部就是 `SendRevision`：`message.beforeSend` 照常执行，有警告时界面显示「仍然发送」，确认后走 `SendAcknowledgedRevision`，仍绑定同一版；之后进入发件箱，照常有 10 秒撤销和至多一次（[0006](0006-send-at-most-once.md)）。审计行和发件箱条目在同一个事务里写入，来源是 `ui`，动作是 `ApproveDraft`。

**只有界面能批准。** `ApproveDraft` 在 `rpcbind` 的 `uiOnly` 里，`full` 和 `mcp` 都调不到。批准代表用户的一次点击，程序不能替自己批准。`full` 角色本来就能用 `SendRevision` 发信（[0003](0003-no-extension-can-send.md) 的例外），所以这不是给 `full` 少了什么能力，只是让「批准」这个名字名副其实；`mcp` 能不能发仍只由「通过 MCP 发送」决定（[0023](0023-mcp-send-setting.md)）。

## Considered Options

- **IMAP keyword**（#671 的原提议）：别的客户端也能看到标记，但能被任何客户端伪造或去掉，草稿也不上服务器。
- **先做成插件卡片**：插件不能发信，只能做标签，「批准并发送」做不了。
- **用户编辑后去掉标记**：见上文，标记会因为一次小改动或自动保存而消失。
- **按内容哈希绑定批准**：revision 已经随每次修改（包括附件）加一，撰写窗口、MCP 发送确认和插件的 `updateDraft` 都用它，没有必要再引入一种版本标识。

## Consequences

- 不新增 egress：每次发送仍要用户在界面上点击，Wit、插件、`mcp` 都不能触发 `ApproveDraft`。
- 卡片显示草稿会发往的全部地址（收件人、抄送、密送），批准前用户能看到每一个目的地。
- 程序写草稿（包括增删附件、换发件账户）时发布 `drafts.changed` 事件，打开着的会话会刷新，卡片始终是将要发出的那一版。
- 新建（`new`）草稿不属于任何会话，只在草稿文件夹里显示标记和按钮。
- 定时发送（#670）以后在这张卡片上加「稍后发送…」，同样要绑定 revision。
