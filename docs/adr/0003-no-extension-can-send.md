# 任何扩展都不能发信

Godwit 不向插件、MCP 和 Wit 提供发信能力：插件的 `mail` 权限只有 `read` 和 `write`，没有 `send`；MCP 没有 `Send`，也不能删除、移动、改设置或处理审批；Wit 只能创建或修改草稿。发送永远由用户在撰写窗口亲手点击（或按 ⌘Enter）触发。这样即使模型被邮件里的 prompt 注入操控，最坏也只能留下一封草稿。

MCP 部分已由 [0023](0023-mcp-send-setting.md) 修订：`godwit mcp` 可以请求发送，默认每次由用户在 Godwit 里确认，用户也可以改成不允许或直接发送。插件和 Wit 不变。

另一个例外是本机 API 的 `full` 角色（见 [0002](0002-single-owner-local-api.md)）：它代表用户自己的程序，可以发送，所有这类发送都记审计。

`message.beforeSend` Hook 可以返回 `warn`（用户可以「仍然发送」）或 `block`（只能修改草稿或停用该插件），但不能替用户发送。

## 会在之后自动外发的持久状态，按外发处理

被注入的模型不必自己发信，留下一条以后会替它发信的状态就够了。所以凡是之后会在无人参与时自动外发的持久状态，创建和修改都按外发处理，要和外发一样经用户确认（[0004](0004-permission-gateway-taint.md)），确认时显示将来会发往的收件人或目的域名。这类状态包括规则里的收件人或 URL、插件配置里的目的地、「通过 MCP 发送」这类发信设置，以及能让以后的调用免审批的授权。inbox-zero 把收件人写死的转发规则判为低风险、免确认，`mcp:write` 也能建转发规则，就是这条缝隙。

目前这类状态都只能由用户在设置里或通过 `full` 角色修改：「通过 MCP 发送」、MCP 服务器和信任的只读工具不在 `mcp` 角色的白名单里；插件只能读、不能改自己的配置，能访问的主机只来自 manifest 的 `net`，`net` 一变就要重新授权；「本次对话都允许」只能授予只写本地、没有目的地的工具（现在只有 `create_draft`）。以后新增规则、定时发送、自动回复等，都按本段处理。
