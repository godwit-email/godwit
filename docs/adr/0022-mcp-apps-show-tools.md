# godwit mcp 只给展示工具挂界面，正文按纯文本渲染

`godwit mcp` 通过 MCP Apps 扩展提供界面，目的是让用户在 Claude、ChatGPT 等宿主里核对 agent 引用的原邮件，并审阅它写的草稿。界面只挂在两个新的**展示工具**上：`show_mail`（一封邮件或一个会话）和 `show_draft`（一封草稿）。现有 10 个工具保持纯数据接口，不挂 `_meta.ui.resourceUri`。宿主每调用一次挂了界面的工具就渲染一张卡片，而模型翻信箱时会连续调用读取工具，所以界面要由模型在用户想看时显式打开，不能跟着读取一起出现。

视图的数据只取自工具结果的 `content` 文本，格式和现有工具相同，邮件派生的字段都在 `<untrusted_email>` 里，视图自己解析。翻页、展开其他邮件、刷新草稿都在视图里通过宿主回调现有读取工具完成，不再弹出新卡片。

## Considered Options

- **给读取和草稿工具直接挂界面**：最省事，但模型连续调用 `list_threads`、`search`、`get_message` 时会刷屏。不同宿主怎么复用同一个 `ui://` 资源的卡片，规范没有保证。
- **视图数据放在 `structuredContent`**：结构最清楚，但宿主通常会把它交给模型，邮件派生的值就出现在标记外面，破坏 `mcpserver` 的「结果只有文本」约束。
- **视图数据放在结果的 `_meta`**：规范的本意是不进模型上下文，但各宿主的实际行为没有统一保证，安全不能押在宿主身上。
- **只做草稿界面**：风险最小，但「看原文」恰恰是用户在宿主里最需要的：核对 agent 的转述、消除搜索歧义、选定回复对象。

## Consequences

- **只渲染纯文本**：正文、主题、地址一律作为文本节点渲染，保留换行；不解析 HTML、Markdown 和图片，链接不可点击。`mcp` 角色本来就只拿得到 `GetMessageText`，这个决定不新增、也不放宽任何本机 API 方法（[0002](0002-single-owner-local-api.md)）。[0013](0013-web-trust-levels.md) 的规则延伸到宿主：宿主的 iframe 允许脚本、能回调工具，邮件 HTML 永远不进去。
- **不联网**：界面是 `go:embed` 进二进制的单个 HTML 文件，脚本和样式全部内联，不声明任何 `connectDomains` / `resourceDomains`，所以不加载远程图片，也就没有跟踪像素。
- **视图不往模型送内容**：不调用 `ui/message` 和 `ui/update-model-context`，打开、滚动、展开邮件都不会把正文回灌给模型，也不能把邮件内容冒充成用户的话。
- **发送按设置**（[0023](0023-mcp-send-setting.md)）：草稿卡片的「发送」按钮调用 `send_draft`，按「通过 MCP 发送」设置处理；设为不允许时按钮不可用，提示「在 Godwit 中发送」。第一期卡片不能编辑；以后如果在卡片里编辑，走 `update_draft` 和它的 revision 冲突检查。
- `get_thread` 不含正文，视图按需调用 `get_message`；正文超过 64 KB 被截断时，视图要明确标出。
- 不支持这个扩展的宿主会忽略 `_meta`，`show_*` 照样返回同格式的文本，不需要按客户端能力分支。
- 邮件一进宿主的界面，就由宿主处理，不再受 Godwit 控制；用户把 `godwit mcp` 接进哪个宿主，就等于把读到的邮件交给了哪个宿主，这一点和现有读取工具一样。
- 以后再看：搜索和线程结果的可点选列表、草稿的轻量编辑；HTML 正文默认不排期。
