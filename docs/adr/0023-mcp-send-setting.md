# MCP 能否发送由用户设置决定，默认每次在 Godwit 里确认

`godwit mcp` 增加 `send_draft(draft_id, revision)`。卡片上的「发送」按钮（[0022](0022-mcp-apps-show-tools.md)）调用的也是它：视图的点击经宿主转成 `tools/call`，到 Godwit 这里和模型自己调用分不出来，所以两者只能用同一条规则。规则由「本机 API」设置里的 **「通过 MCP 发送」** 决定，判定在拥有者的 core 里，`godwit mcp` 进程说了不算：

- **不允许**：返回错误，提示用户在 Godwit 里打开。
- **每次确认**（默认）：创建一次审批，绑定这封草稿当时的 revision。Godwit 把确认窗口提到最前，同时发一条系统通知指向它（点通知打开窗口）。窗口显示发件账户、全部收件人、主题和正文，用户点「发送」后才进入发件箱。工具立即返回「等待用户在 Godwit 中确认」，不阻塞到确认为止。
- **直接发送**：不经确认直接进入发件箱，审计记为 MCP 发送。

不论哪一档，之后都照常走 [0006](0006-send-at-most-once.md) 的至多一次。

## Considered Options

- **永远不能发送**（原 [0003](0003-no-extension-can-send.md)）：用户在宿主里写好、看过草稿，还要切回 Godwit 找到这封草稿再发，体验太差。
- **只让卡片按钮发送，模型不能调用**：MCP Apps 能把工具标成仅视图可见，但只靠宿主执行，Godwit 无法检查；被注入的模型照样可能调到。
- **系统通知上直接点「发送」**：只要一次点击、不用切窗口，但通知里放不下正文，用户会在看不到内容的情况下发出；mygo 的通知目前也没有操作按钮。
- **按收件人自动分级**（发过信的地址直发，新地址确认）：可以减少确认次数，但规则不容易解释，「发过信」也要先可靠地识别出来；留作以后在「每次确认」上的优化。

## Consequences

- 确认窗口要把收件人放在最显眼的位置，第一次发给的地址单独标出来。这一步的意义在于用户真的看一眼，确认窗口不能做成随手一点就过。
- 审批在草稿再被修改（revision 变化）或 10 分钟无人处理时失效，用户确认的永远是将要发出的那一版。
- `--headless` 没有确认窗口，「每次确认」等于不允许。
- 「直接发送」意味着：被邮件里的 prompt 注入操控的 AI 工具，可以不经确认以用户的名义发信，包括发给陌生地址；这时 [0004](0004-permission-gateway-taint.md) 的外发审批也不再生效。选这一档时设置页要明确说明这个风险。
- `mcp` 角色的方法白名单（[0002](0002-single-owner-local-api.md)）新增一个请求发送的方法，其余不变：仍然不能删除、移动、改设置或处理审批。插件和 Wit 仍然不能发送。
- 设置文案（中文）：
  - 标题「通过 MCP 发送」，选项「不允许 / 每次确认 / 直接发送」。
  - 说明：「Claude、ChatGPT 等通过 MCP 接入的 AI 工具请求发送草稿时如何处理。选择『每次确认』时，Godwit 会弹出确认窗口，由你核对收件人和内容后发送。」
  - 选「直接发送」时的提示：「AI 工具读过的邮件里可能藏着诱导它发信的内容。选择后，它可以不经你确认就以你的名义发信，包括发给陌生地址。」
  - `settings_local_api_help` 里「只能读取邮件和创建草稿，不能发送」改为「可以读取邮件和写草稿，能否发送见下方设置」。
