# Wit 的两个绑定保持两个 facade，不抽作用域接口

撰写窗口的 Wit 面板（`webui.ComposePage`）和 Wit 页（`webui.WitPage`）有一批同名方法，看上去像一份实现的两份拷贝。核实后，真正相同的只有几个薄包装（Models、CheckCited、OpenCited、SearchMail、OpenModels），逻辑已经在共享函数里（`modelChoices`、`checkCited`、`searchMail`）；其余方法的差异都是 [0013](0013-web-trust-levels.md) 按调用者限权的正当结果，所以两者各自保留，不抽 `witScope` / `witOps` 一类的接口。

## Considered Options

- **一份实现，两个作用域 adapter**（`resolve(ctx)` 给出服务和归属判断，共享的操作类型嵌入两个绑定）：省下约 30 行包装，但多一层接口；mygo 会绑定嵌入结构体的提升方法，可它们的源码位置是 `<autogenerated>`，生成的 `mygo.ts` 会丢掉参数名和文档注释，想保住还得每个方法留一行转发。
- **网页侧把 Panel 的回调收成一个 `WitHost` 对象**：Panel 的 props 本来就按能力可选（审阅卡片、本次对话都允许、/ 菜单只有一个宿主有），撰写窗口的审批还要把 `BodyChange` 应用到编辑器，收成对象只是换个装法。

## Consequences

- 审批的作用域有意不同：撰写窗口可以审批这封草稿任一对话里待处理的项（⌘K 的对话也算），在会话锁下进行；Wit 页只认它当前 follow 的对话，切走之后不能再审批旧对话，由 `decideMu` 串行。不要把两者「统一」。
- 新增 Wit 方法时，如果只是共享逻辑加调用者检查，就把逻辑放进包级函数，两个绑定各写一个薄包装。
