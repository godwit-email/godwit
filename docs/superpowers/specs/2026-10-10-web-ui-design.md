# Godwit 的网页界面：设计

日期：2026-10-10 · 状态：待评审 · 上位文档：`2026-10-08-godwit-design.md`

Godwit 的主窗口是 mygo 原生界面。三处更适合用网页实现，本文是它们共同的设计：

- **撰写窗口**：每封草稿一个独立窗口，整窗网页（§B）。
- **Wit 页**：主窗口里 Wit 的内容区，嵌入的网页（§D）。
- **阅读区**：主窗口里邮件会话的内容，嵌入的网页（§E）。

§A 是三者共用的基础，§C 是两处「嵌入主窗口」共用的基础。实现拆成多份计划（§F）。

---

## A. 共同基础

### A1. 为什么、做什么

- **撰写**：自研编辑器在中文输入、粘贴、拼写检查、撤销、表格图片、无障碍上很难达到成熟编辑器的水准；独立窗口能同时写多封、对照原邮件。
- **Wit**：流式输出、Markdown、表格、代码块、工具调用、审批卡片，网页里都是现成的组件。
- **阅读**：现在的渲染把邮件 HTML 压平成我们的文档模型，多栏、表格排版、背景、按钮样式都会丢；网页能按原样显示。撰写也换成网页后，写的和看的用同一个引擎。

**不做**：主窗口其余部分（顶栏、图标栏、侧栏、邮件列表、设置）保持原生；联系人自动补全（core 还没有联系人能力）；新增撰写格式；拖放附件；邮件深色反色；按发件人永久放行远程图片。

**行为对等**：撰写、Wit、阅读现有的全部行为都保留，旧测试覆盖的每条行为在新实现里都有对应测试（§A7）。

### A2. 关键决定

| 决定 | 选择 | 理由 |
|---|---|---|
| 前端栈 | React 19、TypeScript、Vite、shadcn/ui（Base UI 版本，Tailwind v4）、TanStack Query | 我们的 token 本来就照 shadcn 定义 |
| 组件来源 | shadcn 组件（含聊天类：`message`、`message-scroller`、`bubble`、`attachment`、`input-group`、`marker`）都由 Bun 脚本调用 shadcn CLI 生成，**生成的文件不手改**；外观只靠主题变量，行为差异在我们自己的目录里包一层 | 与上游保持一致，升级只需重新生成 |
| 前端结构 | Vite 多入口，每种页面一个入口：`compose.html`、`wit.html`、`reader.html`；共享代码在 `src/shared/`、`src/wit/` | 每个页面只加载自己的代码；不同入口有不同的信任级别与 CSP（§A5） |
| 撰写编辑器 | Plate（Slate） | 组件即 shadcn 风格；自带「建议」（修订）与 AI 菜单，对应 Wit 的修订与 ⌘K；Safari 内核下中文输入已实测正常 |
| 聊天界面 | shadcn 的聊天类组件 + `src/wit/` 里自己组合的工具调用、审批、引用卡片 + `useChat` + 自定义 `ChatTransport`（`WitTransport`）；Markdown 用 Streamdown | 不引入 AI Elements：shadcn 已有消息、滚动、输入、附件组件，且同为 Base UI、同一套主题变量和图标（AI Elements 基于 Radix 与 lucide）；只有一个生成来源；`useChat` 现成管理流式状态、停止、出错；智能体循环留在 Go（不写 AI SDK provider） |
| 包管理与构建 | Bun；`web/` 目录；用 mygo CLI（`go tool mygo dev` / `build` / `generate`，版本由 `go.mod` 的 tool 依赖固定）构建：先构建前端、嵌入 `web/dist`、生成 TS 客户端 | mygo 现成的流程，不自己拼；以后发版的打包、签名也用它 |
| 内容的权威 | Go 端。网页只是视图 | 沿用现有的保存、版本、冲突、审批、对话存储 |

### A3. 页面与 Go 的通信

所有页面都用 **mygo 绑定的服务**（`mygo.Bind`），`mygo generate` 生成 TypeScript 客户端（提交入库）：整窗网页如此，嵌入主窗口的网页（mygo #205 的 `ui.WebView`，§C）的页面也是完整的 mygo 页面，同样能调用绑定的方法、接收事件。

**按页面限权**：绑定的服务对所有可信页面可见，所以权限在 Go 端按调用者判定：
- 撰写窗口的方法用 `mygo.CallerWindow(ctx)` 找到窗口，只作用于该窗口绑定的草稿；
- 嵌入网页的方法用 `mygo.CallerPage(ctx)` 找到页面；Go 端登记每个页面的**角色**（`wit`、`reader`）及其上下文（如阅读区当前的会话），每个服务方法先核对角色，不符即拒绝。

网页端测试用 Vitest 的模块替身替换生成的客户端。

### A4. 主题

- Go 端从 `internal/theme` 生成 shadcn 的 CSS 变量（`--background`、`--foreground`、`--muted-foreground`、`--border`、`--input`、`--ring`、`--primary`、圆角与阴影档位等），浅色与深色各一套，加上字号与密度。
- 页面加载时取一套，`theme` 事件推送变化。外观跟随应用设置（不是只跟随系统），与原生界面始终一致。
- **字体用系统字体**，不自己定义：网页用 `system-ui`（macOS 为 SF 与苹方，Windows 为 Segoe UI 与微软雅黑），等宽用 `ui-monospace`。原生界面同步去掉内嵌的 Geist（主题不再指定字体、不再注册字体文件，`Geist Mono` 的几处换成系统等宽字体），两边一致。

### A5. 安全

**信任级别按入口划分**：

| 入口 | 页面 | 能调用 | CSP |
|---|---|---|---|
| `compose.html` | 整窗网页 | `Compose`，只限本窗口的草稿 | 只加载打包的脚本与样式；`img-src data: blob:` 与本地附件协议；无任何远程请求 |
| `wit.html` | 嵌入网页，角色 `wit` | Wit 的一组方法 | 同上 |
| `reader.html` | 嵌入网页，角色 `reader` | 阅读区的动作（展开、显示图片、附件、链接、标记已读等），只限页面登记的会话 | 同上；邮件正文另在沙箱 iframe 里（§E3） |

**规则**：

1. **邮件 HTML 永远不进可信页面的文档**：撰写窗口里引用的原邮件以纯文本显示；正文与粘贴内容只经过反序列化变成 Plate 的数据结构，由 React 渲染（自动转义），不使用 `dangerouslySetInnerHTML`。阅读区的邮件正文只放在沙箱 iframe 里：mygo 规定 iframe 永远不能调用 Go 方法，且我们不允许 iframe 运行脚本。
2. **模型输出按不可信内容渲染**：模型读过邮件，输出可能被提示注入。Streamdown 收紧为：链接只允许 http、https、mailto，点击一律走 Go 的确认后用系统浏览器打开；不显示图片；保留 HTML 清洗插件、不允许原始 HTML。引用的邮件用我们自己的卡片显示，疑似注入的来源标出「已作为数据处理」（与现在一致）。
3. **不跳转**：页面内导航一律拦截（页面的 `OnWillNavigate`）；`window.open` 拒绝；链接只经 Go 确认后用系统浏览器打开。
4. **按页面限权**（§A3）：角色不符的调用一律拒绝，并有测试覆盖。
5. **发送仍需亲手点击**：Wit 不能发送；`send` 只由撰写窗口的发送按钮或 ⌘Enter 触发。

### A6. 工程与构建

- **目录**：`web/`（Vite 多入口）：
  - 生成的（不手改）：`src/components/ui/`（shadcn，Base UI 版本）；生成脚本 `scripts/components.ts` 列出要生成的组件，可重复执行；
  - 我们自己的：`src/shared/`（主题变量、工具函数、对生成组件的包装）、`src/wit/`（Wit 组件与 `WitTransport`）、`src/compose/`、`src/wit-page/`、`src/reader/`，后三者各对应一个 HTML 入口。`web/src/mygo.ts` 为生成的客户端（提交入库）。
- **构建**：根目录的 `mygo.json` 配置 mygo CLI：`main` 为 `./cmd/godwit`，`devCommand` 起 Vite，`devUrl` 指向它，`buildCommand` 安装依赖并构建前端，`frontendDist` 为 `web/dist`，`bindings` 为 `web/src/mygo.ts`。`go tool mygo dev` 开发（热更新、Go 改动后重新生成客户端并重启），`go tool mygo build` 出正式包。
- **前端依赖是编译前提**：原生界面的图标直接从 `web/node_modules/remixicon` 嵌入（用到的逐个列出），所以任何 Go 的编译、`go test`、`go vet` 之前都要先 `bun install`；`mise` 任务与 CI 都先安装。不再有「前端未构建」的状态。
- **命令**：`mise` 任务 `web:install`、`dev`、`build`、`web:test`、`web:check`，分别包装上面的命令。
- **CI**：三个平台先 `bun install`，再跑 Go 的检查与测试，并 `go tool mygo build` 确认能出包；新增网页任务（类型检查、lint、Vitest）；检查生成的客户端与 Go 代码一致、组件生成目录无手改。
- **体积**：React、Plate、shadcn、Streamdown 打包后约 1～2 MB，嵌入二进制可以接受。

### A7. 测试

- **Go 端**：服务方法在 core 测试环境里测，按窗口或入口限权、越权调用被拒。
- **网页端**：Vitest + Testing Library（jsdom），用模块替身替换生成的客户端。
- **端到端**（macOS，可选 CI 任务）：真实窗口加脚本驱动（整窗网页用 `mygo.EvalAs`，嵌入网页用 `Call`）。
- **对照表**：现有 `app/compose_test.go`、`app/compose_wit_test.go`、`app/ask_test.go`、`app/wit_*_test.go`、`app/reader_test.go`、`app/reader_ai_test.go` 的每个测试，在对应计划里列出新测试中的对应项。
- **输入法检查清单**：你在 Safari 里试过的边界情况整理成清单，升级 Plate 时人工过一遍。

## B. 撰写窗口

### B1. 窗口与生命周期

- **打开**：现在所有导航到 `PageCompose` 的地方（新建、回复、全部回复、转发、快速回复、插件动作返回草稿、mailto、草稿列表、菜单与托盘的「写邮件」⌘N）改为调用 `App.OpenCompose(draftID)`：已有该草稿的窗口就聚焦，否则新建窗口。`PageCompose` 路由与主窗口里的撰写视图删除。
- **窗口**：mygo 现有的网页窗口，加载 `/compose.html`（草稿由 Go 端按窗口绑定，URL 不带草稿 ID）；标题为主题（空时「新邮件」）；默认 860×720，最小 640×480，位置和大小按 `StateKey: "compose"` 记忆；新窗口相对上一个错开。macOS 用透明标题栏，网页自己画顶栏（`--app-region: drag`），与主窗口观感一致。整窗网页不依赖 mygo #205。
- **关闭**（⌘W 或红灯）：先让网页提交未保存的输入并等保存完成；保存失败时询问「有修改没有保存」（关闭 / 返回）。发送成功或丢弃后窗口自动关闭。**空草稿自动删除**：关闭时草稿没有收件人、主题、正文和附件（新建或回复带出的引用与签名不算内容），就删除它，不留在草稿列表里；退出应用时同样处理。
- **退出应用**：沿用 `flushDrafts` 的语义，等所有撰写窗口保存完；有失败时询问。
- **窗口与草稿的绑定**：Go 端维护 `window ID → draftID`。草稿被删除（别处丢弃）时关闭其窗口。

### B2. `Compose` 服务

**每个方法都只作用于调用者窗口绑定的草稿**，页面不传 draftID。

| 方法（TS 名） | 作用 | 对应 core |
|---|---|---|
| `load(): ComposeState` | 账户列表、草稿字段、可编辑正文 HTML、引用与签名（纯文本）、附件、revision、设置（是否有模型、语言）、主题 | `GetDraft`、`SplitDraft`、`ListAccounts` |
| `save(edit): SaveResult` | 保存字段与正文，带 revision；返回新 revision 或冲突 | `SaveDraft`（`ErrStaleDraft` → 冲突） |
| `resolveConflict(keepMine)` | 保留我的版本 / 使用最新版本 | 现有 `KeepMine` / `useLatest` 语义 |
| `setAccount(id)` | 切换发件账户，换签名 | `SetDraftAccount` |
| `addAttachments()` | 弹原生多选文件对话框（挂在本窗口），逐个添加 | `plat.OpenFiles`、`AddAttachment` |
| `removeAttachment(id)` | 删除附件 | `RemoveAttachment` |
| `send(digest?)` | 发送；带 digest 即「仍然发送」 | `Send` / `SendAcknowledged` |
| `discard()` | 丢弃草稿 | `DeleteDraft` |
| `assist(input)`、`skill(name, lang?)`、`rewriteSelection(html, instruction)` | Wit；返回 `Channel<WitEvent>` 流式事件 | `Assist`、`AssistSkill`、`RewriteSelection` |
| `witHistory()` | 草稿的 Wit 对话历史（UI 消息形状）与是否有进行中的回复 | `ListConversations`、`ListApprovals`、对话消息 |
| `decide(approvalID, accept)`、`applyEdited(approvalID, html)`、`undoAssist()`、`stop()` | 审批与撤销 | `ResolveApproval`、`ApplyEditedProposal`、`UndoLastAssist`、`CancelRun` |
| `openLink(url)` | 用户确认后用系统浏览器打开 | 现有链接确认 |

**事件（Go → 网页）**：`draftChanged`（Wit 应用或别处保存后，网页按现有重载规则决定是否重载）、`theme`、`closing`（请网页立即提交输入）。

**保存规则**照搬 `draftsaver`：停止输入 1 秒后保存；输入法合成中不保存；写入按草稿串行；关闭和发送前先 flush；发送时冻结编辑并提示「正在发送，暂不能修改」。这些放在网页端的一个小状态机里，由 Go 端的 revision 校验兜底。

### B3. 界面与编辑器

- **字段**：发件人（账户下拉）、收件人 / 抄送 / 密送 / 回复地址（标签式输入：逗号、回车、失焦提交，重复跳过，无效地址标红并在下方列出；抄送等默认折叠，有值时展开）、主题。
- **Plate 插件**：段落、粗体、斜体、链接、有序 / 无序列表、引用块，和 `FromComposeHTML` 保留的格式一一对应；不启用其他格式。
- **HTML 进出**：载入时用 Plate 的 HTML 反序列化（在 `DOMParser` 生成的惰性文档上进行，不执行任何脚本）；保存时序列化为 HTML 交给 Go，Go 用 `SanitizeCompose` 清洗后存。粘贴走同一条反序列化路径。
- **引用与签名**：和现在一样不进编辑器，以只读纯文本显示在正文下方（引用默认折叠）。
- **工具栏**：与现有同样的按钮（粗体、斜体、链接、无序列表、有序列表、引用、附件）；链接用 Popover 输入。
- **附件**：文件名、大小、删除；超过 25 MB 时提示。
- **发送区**：发送、丢弃（确认对话框）、「发送仍需你亲手点击」说明；插件警告列表与「仍然发送」、拦截提示、保存状态（正在保存… / 草稿已保存 · HH:mm / 未保存）、冲突提示（保留我的 / 使用最新 / 重试）。
- **快捷键**：⌘B / ⌘I；⌘K（有选区且配置了模型时打开 Wit 改写，和现在一样；否则插入链接）；⌘Enter 发送；⌘W 关闭；Esc 关闭弹出层。撤销、复制、粘贴走系统「编辑」菜单（整窗网页走 mygo 的常规路径，计划 1 先实测）。

### B4. 撰写里的 Wit

右侧是 Wit 面板（有模型服务时显示），用 §D1 的组件，在窄容器里自动收紧；撰写特有的部分通过插槽传入。

- 面板内容：上下文标签（原邮件、附件、往来邮件数）、调整 ▾（正式、友好、更短、更长、校对）、翻译 ▾、自由输入、流式回答、审批卡片。
- **正文里的修订**在编辑器里显示：
  - 是「逐词修订」还是「整体重写」**由 Go 端判定**，沿用现有 `newProposal` 的规则（`worddiff`，块类型不变且改动比例 ≤ 0.5 为逐词），随审批一起发给网页。
  - 逐词修订用 Plate 的「建议」能力在正文里标出插入与删除，每处可单独接受或拒绝；全部接受 / 全部拒绝走 `decide`，部分接受时网页生成结果 HTML 走 `applyEdited`。
  - 整体重写：正文只读显示新版本，可切换「对比原文」，整体接受或拒绝。
  - 面板里的确认卡片与正文操作同一个审批。
- **⌘K 改写选区**：Plate 的 AI 菜单形态，在正文里原地弹出。网页先保存，再把**带两个选区标记的正文 HTML** 发给 Go；Go 去掉标记、清洗后算出 core 需要的字节偏移，调用 `RewriteSelection`。标记用不会被清洗规则保留的私有元素。
- **运行中锁定**、**首次生成自动应用**、**已应用可撤销**、**重载规则**（新读覆盖旧读、本地有编辑时保留本地）照搬现有逻辑。

## C. 嵌入主窗口的网页：共同基础

### C1. 依赖

主窗口是原生界面，网页要嵌入其中：用 mygo PR #205（作者本人提交）的 `Window.NewWebView` 与 `ui.WebView`。它把网页放在原生画布**下面**，画布在网页处挖洞，所以：
- 画在网页之后的原生内容（下拉菜单、Select、对话框与遮罩、提示、Toast、角标）都显示在网页**上面**，遮罩挡住网页的点击；
- 滚动容器和圆角会裁剪网页；
- 嵌入的页面是完整的 mygo 页面，能调用绑定的方法；
- 系统「编辑」菜单（撤销、复制、粘贴、全选）、中文输入法在网页里正常工作。

以上在 macOS 上用探针实测确认。在它合并发版之前，`go.mod` 用 `replace` 指向 `github.com/baranwang/mygo` 的 `webview-hole` 分支（即 #205 的代码）；合并后去掉 `replace`，核对 API 差异再切回。

### C2. 用法与限制

- **创建一次、按需显示**：每个嵌入页面像窗口一样在启动时（或首次需要时）创建一次；视图里不构建它时自动隐藏并保留页面。阅读区的多个正文按需创建、用完销毁（§E）。
- **布局**：`ui.WebView` 是普通的布局元素，可设高度、圆角、边框；页面显示在内容框里。
- **滚动的转交**：网页视图会留住它自己用不上的滚轮（网页没东西可滚，或已滚到头），不交还给外面的原生滚动区域（#205 的现状，已在 macOS 实测）。嵌在原生滚动区域里的页面（阅读区正文）由页面监听滚轮，自己滚不了时把滚动量交给 Go，Go 推动外层的原生滚动；同一显示帧内的滚动量合并，每帧最多调用一次。实测手感可以接受（高配机器上有轻微掉帧）。铺满区域、自己滚动的页面（Wit 页）不需要。待 mygo 修好后去掉。
- **焦点**：点击网页时网页获得键盘；Tab 不会从原生控件移进网页（mygo 的已知限制），需要时用 `Focus`。全局快捷键（⌘N、⌘[ / ⌘]、切换页面）在网页里由页面转发给 Go。
- **其他限制**：主窗口的毛玻璃材质透不过网页区域（网页区域本来就是不透明的内容）；辅助技术把网页和原生界面分开读；Windows 上拖到网页上的文件交给原生的拖放目标。

## D. Wit

### D1. 组件（撰写与 Wit 页共用）

放在 `src/wit/`，**只有一种组件，不分形态**：

- **按容器宽度自适应**（CSS 容器查询）：例如「引用的邮件」在够宽时显示为右侧栏（Wit 页），窄时收成回答下方的引用卡片（撰写窗口的侧面板）。
- **场景差异用插槽**：撰写传入上下文标签、调整 ▾、翻译 ▾；Wit 页传入模型选择。组件本身不知道自己在哪里。
- **用到的生成组件**（shadcn）：`message-scroller`（对话滚动、回到底部）、`message` / `bubble`（消息）、`input-group` + `attachment`（输入框与附件）、`button` / `badge`（建议）、`spinner` + `marker`（思考中、状态行）、`collapsible`、`card`、`hover-card`。
- **自己组合的**（`src/wit/`，只组合生成组件，不改它们）：Response（Streamdown 按 §A5 收紧）、ToolCall（`collapsible` + `card`，显示工具名、参数、结果）、Approval（`card` + `button`，审批卡片）、Citation（`hover-card` + 我们的邮件卡片）。
- **我们自己的**：权限说明、疑似注入提示等，以及对生成组件的包装。

### D2. `WitTransport`

`useChat` 管理一段对话的消息与流式状态，它的 `ChatTransport` 由我们实现，底层调用生成的客户端（§A3），撰写窗口和 Wit 页用同一个实现：

- `sendMessages`：把用户输入交给 Go，返回由 Go 事件翻译成的 `UIMessageChunk` 流；
- `reconnectToStream`：页面重开或切回时，若对话有进行中的回复，订阅它继续显示；
- 打开对话时，用 Go 端的历史初始化 `useChat` 的 `messages`（工具调用与结果、引用、审批状态都带上）；
- 审批：用户在确认卡片上的选择交给 Go（`decide`），Go 继续运行并推送后续事件。

**事件映射**（Go 的 `WitEvent` → AI SDK 消息片段；片段的确切名称以当时 AI SDK 版本为准，在计划里核对）：

| Go 事件 | 前端片段 |
|---|---|
| `text` | 文本片段的开始 / 增量 / 结束 |
| `tool_call` | 工具片段，状态「输入就绪」（工具名即 `search_mail` 等） |
| `tool_result` | 同一工具片段，状态「输出就绪」 |
| `interrupted` + `Approvals` | 对应工具片段，状态「等待批准」，附审批 ID、摘要、目的地 |
| `Citations` | 引用片段（自定义数据片段：邮件 ID、主题、发件人、日期、是否疑似注入） |
| `context`（使用的模型）、`draft`、`account` | 消息元数据 / 自定义数据片段 |
| `done` | 结束 |
| `error` | 出错（可重试） |

### D3. Wit 页（完整版）

- **原生部分**：左侧对话列表侧栏（Wit 标题、新对话、最近对话）与顶栏的对话标题、权限说明。侧栏就是现有的原生侧栏，宽度与其他页面共用同一个可拖动的宽度，自然同步。
- **网页部分**（`wit.html`，嵌入，角色 `wit`）：右侧整个内容区：对话（§D1 的组件，在宽容器里展开）、审批卡片、右边「引用的邮件」栏、底部悬浮输入框（`float` 阴影、`2xl` 圆角，与现在一致）、模型选择。
- **可调用的方法**（角色 `wit`）：发送问题、订阅与取消回复、对话历史、审批、新建对话（返回 ID，由原生侧栏刷新）、打开引用的邮件、打开链接、设置相关只读信息（模型、语言）。
- **打开引用的邮件**：页面调用方法，由原生端导航到阅读区打开那封邮件（与现在一致）。
- **没有模型服务时**：显示现在的空状态（「Wit 需要模型服务才能回答」与「添加模型服务」），按钮由原生端导航到设置。

## E. 阅读区

### E1. 原生与网页的分工

**只有邮件正文是网页**，其余保持原生，阅读区整体仍是原生滚动：

- **原生**：会话标题、工具栏、每封邮件的发件人行与时间（展开 / 折叠）、AI 总结与插件卡片、远程图片拦截提示、附件、即时回复。
- **网页**（`reader.html`，嵌入，角色 `reader`）：每封**展开的**邮件一个正文页面，放在原生布局中原来正文的位置；高度随内容撑开，由原生滚动带着走，滚出可视区的部分被裁剪（§C1）。折叠的邮件只显示原生的摘要行，不创建网页。
- 纯文本邮件也走同一个页面（以等宽或常规字体按主题显示），两种邮件外观一致。

### E2. 正文页面

- 页面加载后向 Go 登记角色与它负责的邮件；Go 推送清洗后的正文 HTML、远程图片状态与主题。
- 页面把正文放进**沙箱 iframe**，量出高度后调用方法告诉 Go，原生据此设置 `ui.WebView` 的高度；正文图片加载、窗口宽度变化时重新上报。
- **可调用的方法**（角色 `reader`，只限登记的邮件）：上报高度、转交滚轮（§C2）、打开链接（Go 确认后用系统浏览器；`mailto:` 打开撰写窗口）、取远程图片（见下）、取内嵌图片。
- 选中与复制由网页完成（系统「编辑」菜单可用）；「在邮件里查找」（⌘F）本期由页面实现简单的查找高亮。

### E3. 邮件正文的隔离

- 沙箱 iframe（`srcdoc`，`sandbox="allow-same-origin"`，不允许脚本）：邮件的 CSS 碰不到页面；邮件里不会运行任何脚本；iframe 永远不能调用 Go。父页面同源，能量高度、拦下 iframe 里的链接点击转给 Go。
- **远程资源**：CSP 不允许任何远程请求（iframe 继承）。图片走 Go 的代理协议（如 `godwit-img://`）：只有用户点了「显示图片」的那封邮件，Go 才代为下载并返回，不带 Cookie 与 Referer；没放行时一律不响应。内嵌图片（`cid:`）由 Go 从邮件里取出，同样走该协议。
- **外观**：HTML 邮件保持原样放在白底上，深色模式下不反色；纯文本邮件跟随主题。
- 现有清洗（`mail.Sanitize`）继续在 Go 端执行，iframe 隔离是第二道防线。

### E4. 与现在的差异

- HTML 邮件按原样显示，不再压平成我们的文档模型。
- 打印、按发件人永久放行图片不在本期。

## G. 风险与待验证

- **WebView2（Windows）与 WebKitGTK（Linux）**：没有 Windows 机器实测，依赖 CI 的端到端检查与 #205 作者在三个平台上的测试；Plate 在 Chromium 上最成熟，风险较低。
- **#205 的走向**：可能在合并前改 API；滚轮不转交的问题需反馈给作者。fork 让我们先做；切回时以计划 4 的封装为唯一改动点。
- **系统「编辑」菜单在整窗网页里是否可用**：嵌入网页已确认可用；整窗网页计划 1 再实测。
- **阅读区性能**：长会话里每封展开的邮件一个网页视图，内存与创建耗时要实测（计划 6）；超标时改为只给可见的邮件创建、或回退为整段会话一个页面。
- **Plate、React、AI SDK 版本升级**：锁定版本；升级时过输入法检查清单，`WitTransport` 的映射测试覆盖所有片段。
- **生成客户端需要能运行到 `App.Run`**：`main` 在 `App.Run` 之前不能有副作用，计划 1 核对 `cmd/godwit`。
